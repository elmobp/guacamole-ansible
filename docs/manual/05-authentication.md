# 5. Authentication Methods

Guacamole separates two concerns: **who is this person** (authentication) and **what are they
allowed to do** (authorization). The JDBC database extension always provides authorization
(connections, groups, permissions), and can also provide authentication on its own. Everything
else in this chapter — LDAP, MFA, and the four SSO methods — layers *on top of* the database, and
only ever answers the "who" question; the database is still consulted for the "what".

You can drive all of this interactively instead of hand-editing YAML:

```bash
python3 scripts/configure.py
```

It asks for the hostname, database location, **which primary authentication method** you want,
whether to add MFA, and writes a ready-to-use `host_vars/<hostname>.yml`. It installs nothing and
is safe to re-run at any time — treat it as a guided alternative to everything below, not a
separate mechanism. Full variable-by-variable detail lives in `docs/CONFIGURE.md`
("Single sign-on / federated authentication") and copy-paste blocks in `docs/SCENARIOS.md`
(§4–§6c); this chapter explains the *why* and the IdP-side steps that live outside this repo.

## 5.1 Database authentication (the default)

**What it needs:** nothing extra — this is what you get with every install. Users and passwords
live in the `guacamole_user`/`guacamole_entity` tables, managed via `guac_users` (Chapter 3) or
the UI.

**Test it:** `curl -sk -d 'username=<user>&password=<pass>' https://<host>/api/tokens` should
return `{"authToken": "..."}`.

**Roll back:** nothing to roll back — this is always available underneath any SSO/LDAP layer.

## 5.2 LDAP / Active Directory

**What it needs:** an existing AD/LDAP directory reachable from this host, and a service (bind)
account with read access to search for users.

```yaml
guac_ldap_enabled: true
guac_ldap:
  hostname: "dc1.corp.example dc2.corp.example"   # space-separated for failover
  port: 636
  encryption_method: ssl                           # none | starttls | ssl
  search_bind_dn: "svc-guacamole@corp.example"
  search_bind_password: "{{ vault_ldap_bind_pw }}"
  config_base_dn: "dc=corp,dc=example"
  user_base_dn: "OU=Staff,DC=corp,DC=example"
  username_attribute: sAMAccountName               # AD; use "uid" for OpenLDAP
  user_search_filter: "(&(objectClass=user)(!(objectCategory=computer)))"
  max_search_results: 500
```

**Directory-side steps:** create the `svc-guacamole` service account, grant it read access to
`user_base_dn`, and open outbound `636/tcp` (LDAPS) or `389/tcp` (STARTTLS) from this host to
your DCs — see `docs/FIREWALL.md` O9.

**Test it:** log in as a directory user through the normal login form (LDAP replaces the
credential check; there's no separate LDAP login button).

**Roll back:** set `guac_ldap_enabled: false` and re-run — the extension jar is removed and
database-only login resumes for every account that also has a database password set.

LDAP can *also* just supply group membership for RBAC without being the login mechanism — see
§3.4 and Chapter 13's `guac_user_groups` reference.

## 5.3 TOTP (Google Authenticator-style MFA)

**What it needs:** nothing external — each user's device generates codes locally once enrolled.

```yaml
guac_totp_enabled: true
```

**Test it:** log in; on first login after enabling, the user is prompted to scan a QR code and
enrol. Subsequent logins ask for the 6-digit code after the password.

**Roll back:** `guac_totp_enabled: false` and re-run removes the extension; existing enrolments
are simply no longer checked (they aren't deleted from the database, so re-enabling later doesn't
require re-enrolment for users who never had their TOTP secret cleared).

## 5.4 Duo Security MFA

**What it needs:** a Duo Admin Panel application (Auth API or WebSDK, per your Duo tenant) —
Duo issues an integration key, secret key, and API hostname.

```yaml
guac_duo_enabled: true
guac_duo:
  api_hostname: "api-XXXXXXXX.duosecurity.com"
  integration_key: "{{ vault_duo_ikey }}"
  secret_key: "{{ vault_duo_skey }}"
  application_key: "{{ vault_duo_akey }}"   # any random 40+ char string — generate once, keep stable
```

**Duo-side steps:** create the application in the Duo Admin Panel, copy the three Duo-issued
values into vault, and open outbound `443/tcp` to `*.duosecurity.com` (`docs/FIREWALL.md` O11).
`application_key` is generated by you (not Duo) and must stay the same across restarts — losing
it invalidates in-flight MFA sessions but not user enrolments.

**Test it:** log in with a database/LDAP credential; Duo's push/passcode challenge should appear
next.

**Roll back:** `guac_duo_enabled: false` and re-run.

## 5.5 Single sign-on — one primary method per host

Pick **one**: OpenID Connect, SAML 2.0, X.509 client-certificate, or CAS. Each is validated at
playbook run time — enabling one with missing required keys **fails the run early**, before
Tomcat is touched, rather than leaving you with a half-built, broken login page.

### 5.5a OpenID Connect (Keycloak, Entra ID, Okta, Google, ...)

```yaml
guac_openid_enabled: true
guac_openid:
  authorization_endpoint: "https://idp.example.com/realms/corp/protocol/openid-connect/auth"
  jwks_endpoint:          "https://idp.example.com/realms/corp/protocol/openid-connect/certs"
  issuer:                 "https://idp.example.com/realms/corp"
  client_id:              "guacamole"
  redirect_uri:           "https://guac.example.com/"
  username_claim_type:    "preferred_username"     # or "email"
  groups_claim_type:      "groups"                 # for RBAC, see §3.4
```

**IdP-side steps:** register a confidential or public OIDC client named (e.g.) `guacamole`,
allow the redirect URI `https://<guac_proxy_site>/` **exactly** (trailing slash matters to most
IdPs), and, if you want group-based RBAC, configure the IdP to emit a `groups` claim.

**Test it:** the login page shows an SSO button; clicking it redirects to the IdP, and a
successful IdP login returns to Guacamole already authenticated.

**Roll back:** `guac_openid_enabled: false` and re-run restores the plain login form; database
and (if configured) LDAP/MFA logins are unaffected throughout.

### 5.5b SAML 2.0 (ADFS, Entra ID, Okta, Shibboleth, ...)

```yaml
guac_saml_enabled: true
guac_saml:
  idp_metadata_url: "https://idp.example.com/federationmetadata/2007-06/federationmetadata.xml"
  entity_id:        "https://guac.example.com/"
  callback_url:     "https://guac.example.com/"
  group_attribute:  "groups"
  strict: true
```

If your IdP has no single metadata URL, omit `idp_metadata_url` and set `idp_url` + `entity_id`
instead.

**IdP-side steps:** register a SAML relying party/application with entity ID and ACS
(assertion consumer / callback) URL both equal to `https://<guac_proxy_site>/`; if the IdP
supports metadata exchange, give it the metadata URL rather than typing endpoints by hand.

**Test it:** same as OIDC — an SSO button on the login page, IdP redirect, and a return
authenticated.

**Roll back:** `guac_saml_enabled: false`, re-run. Leave `strict: false` only for a lab/test IdP
— it disables signature/certificate validation on assertions and should never reach production.

### 5.5c X.509 client-certificate / smart card

This method needs a **second TLS vhost** that terminates the client-certificate handshake, since
the browser has to be asked for a certificate on a connection nginx is willing to accept without
one first (see the sequence in Chapter 6).

```yaml
guac_ssl_auth_enabled: true
guac_ssl_auth_domain: "cert.guac.example.com"          # + a *.cert.guac.example.com DNS record
guac_ssl_auth_client_ca: "{{ vault_client_issuing_ca_pem }}"
guac_ssl_auth:
  auth_uri:    "https://cert.guac.example.com/"
  primary_uri: "https://guac.example.com/"
  subject_username_attribute: "CN"
guac_ssl_auth_manage_nginx: true    # let this playbook add the cert-verifying vhost (recommended)
```

**PKI-side steps:** get the issuing CA's certificate (PEM) for whatever CA issues your users'
smart-card/client certificates — this goes in `guac_ssl_auth_client_ca` (vault it). Add the DNS
record for `guac_ssl_auth_domain` (and, in production, a **wildcard** TLS certificate for
`*.<guac_ssl_auth_domain>` — the ssl extension bounces the browser through ephemeral
subdomains during the handshake).

**Test it:** click *"Certificate / Smart Card"* on the login page; the browser prompts for a
client certificate; a certificate whose `CN` (or configured `subject_username_attribute`) matches
a Guacamole username logs straight in.

**Roll back:** `guac_ssl_auth_enabled: false`, re-run — the extra vhost and header-scrubbing rules
are removed from nginx along with the extension jar.

**Security note:** when this is enabled, nginx also scrubs the `X-Client-Certificate` /
`X-Client-Verified` headers on the *normal* vhost, so a client can't fake a verified certificate
by simply setting those headers itself — verification only ever happens on the dedicated cert
vhost.

### 5.5d CAS (Apereo/Jasig)

```yaml
guac_cas_enabled: true
guac_cas:
  authorization_endpoint: "https://cas.example.com/cas"
  redirect_uri:           "https://guac.example.com/"
```

**IdP-side steps:** register `https://<guac_proxy_site>/` as an allowed service URL in the CAS
server's service registry.

**Test it / roll back:** as with the other SSO methods.

## 5.6 Stacking MFA on SSO

TOTP and Duo are independent toggles — either can be layered on top of database, LDAP, *or* any
SSO method by simply also setting `guac_totp_enabled: true` or `guac_duo_enabled: true`. The user
completes the primary method first, then the MFA challenge.

## 5.7 Verifying and troubleshooting

- `docs/CONFIGURE.md` documents every key precisely, including optional/advanced fields not shown
  above (`allowed_clock_skew`, `x509_cert_path`, `subject_base_dn`, ...).
- `docs/SCENARIOS.md` has more complete, ready-to-paste blocks for each method.
- If a method is enabled with a missing required key, the playbook **fails at the
  `guac_extensions` role**, before Tomcat is restarted — read the assertion message, it names the
  exact missing key.
- See Chapter 12 for symptoms like "SSO button doesn't appear" or "extension jar missing after
  enabling a method."
